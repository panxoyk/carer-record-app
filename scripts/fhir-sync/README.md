# FHIR structural sync (local development)

The normal workflow uses two terminals: `pnpm env:up` starts/reuses Supabase and HAPI, seeds HAPI, performs this sync, applies demo assignments and serves the gateway in foreground; then `pnpm app:run` starts Flutter only. `Ctrl+C` in the environment terminal closes its gateway but leaves containers running; reopen `env:up` before relaunching Flutter. `pnpm env:stop` safely stops HAPI and Supabase without deleting volumes. For focused diagnosis, run `node scripts/fhir-sync/generate-sync.mjs --apply` after local Supabase and HAPI are available. The command reads paginated Patient, Encounter and Location resources, writes ignored local SQL, and applies it through `psql` in the exact `supabase_db_carer-record` container. Override that container with `FHIR_SYNC_DB_CONTAINER` when using a deliberately named local project.

The source logical key is `demo-hapi`; UUID namespace input is `demo-hospital\0demo-hapi`, followed by resource type and FHIR `Resource.id`. UUID bytes are the first 128 bits of SHA-256 with RFC 4122 version/variant bits set. `fhir_sources` and the typed link tables are the authority for FHIR identity; `patients.external_reference` is left NULL because it is globally unique and cannot safely represent a multi-source key.

Demo care assignments are applied by `pnpm env:up`; for focused diagnosis, run `node scripts/fhir-sync/generate-sync.mjs --demo-assignments`. It uses `demo-assignments.json`, creates only missing rows, and does not revive an existing revoked/expired decision. It must be run after structural sync.

Focused unit tests: `pnpm fhir:sync:test generate-sync.test.mjs` or `pnpm fhir:sync:test demo-fixture.test.mjs` (selectors are relative to `scripts/fhir-sync/`). The opt-in PostgreSQL rollback integration test is run with `FHIR_SYNC_PG_INTEGRATION=1 pnpm fhir:sync:test`; it requires an already-running, migrated local DB container and does not reset it.

This script is a local demo projection, not the production ingestion worker or clinical-record gateway. Never point it at real clinical data.

## Persistent local HAPI and manual transfer

The development compose uses the same pinned HAPI 8.12 image with H2 at `/data/hapi` on the named `carer-record-hapi-data` volume. A pinned Alpine init container prepares the mount for HAPI UID/GID `65532:65532`. Host-side Node bootstrap uses `PUT` with `If-Match: W/"0"`, verified for HAPI 8.12, to create only missing synthetic fixture identities; startup guards reject an existing container with the wrong datasource or mount before compose recreation. Startup does not migrate the current HAPI environment, purge resources, or replace assignments.

For a deliberate transition, first verify that the source dataset is entirely synthetic, then explicitly export with `node scripts/fhir-sync/hapi-data-transfer.mjs export --confirm-synthetic` to an ignored local file. Check the report's `historyComplete` and resource/history counts; stop and retain the source unchanged if incomplete or unexpected. Restore only into a separately named staging HAPI container with its own new persistent volume using `node scripts/fhir-sync/hapi-data-transfer.mjs restore --input=<ignored-export-file>`. Validate identities/counts before any later cutover; keep the old server and volume intact until then. This is a FHIR resource/history archive, not a full H2/database backup. Logical `Resource.id` is retained where possible, but source `meta.versionId`, all source revisions, and deleted-resource tombstones are not guaranteed to be restored. No automatic purge/recreate is part of app startup.
