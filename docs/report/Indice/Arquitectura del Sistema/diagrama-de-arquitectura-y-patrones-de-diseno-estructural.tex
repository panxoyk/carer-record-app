\subsection{Arquitectura de componentes}

La Figura~\ref{fig:diagrama_arquitectura} presenta los recorridos de sesión, consulta clínica y consulta a la fuente hospitalaria.

\begin{figure}[H]
    \centering
    \resizebox{0.95\textwidth}{!}{%
    \begin{tikzpicture}[
        component/.style={draw, rounded corners, align=center, text width=3.1cm, minimum height=1.15cm, fill=blue!8},
        service/.style={draw, rounded corners, align=center, text width=3.2cm, minimum height=1.15cm, fill=green!10},
        data/.style={draw, rounded corners, align=center, text width=3.2cm, minimum height=1.15cm, fill=violet!10},

        \node[service] (edge) at (4.5,-3) {Edge Function\\pasarela clínica autorizada};

    \end{tikzpicture}%

    \caption{Arquitectura de solución de Carer-Record}
    \label{fig:diagrama_arquitectura}

Flutter intercambia credenciales y sesión con Supabase Auth; mediante un JSON Web Token (JWT) consulta PostgREST/RPC y persiste notas confirmadas en PostgreSQL, donde RLS es la autoridad de autorización. Una función Edge actúa como pasarela: comprueba autorización y vínculos con Supabase y media las consultas y respuestas de la FCE. La demostración utiliza una FCE simulada FHIR R4 en Docker con datos sintéticos.

El ASR y la asistencia de redacción y resumen se ejecutan en el dispositivo. Audio y transcripción sin confirmar permanecen allí; la nota confirmada sí se envía al backend. La FCE conserva el carácter de registro oficial y no recibe escrituras desde Carer-Record.
